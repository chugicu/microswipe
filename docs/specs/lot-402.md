# Lot 402 — ELO officiel à la synchronisation et estimation sur le téléphone

Phase 4. Dépend des lots 308, 309 et 401 (et, par eux, des lots 106, 201, 301, 302, 306, 307, 313 et 315). Domaines de tests obligatoires : **moteur ELO** et **synchronisation**.
Spec écrite en phase 0, lot 4b, conversation 5 (16 novembre 2026). **Lis d'abord `docs/specs/lot-401.md` en entier** : le moteur, ses réglages et son vocabulaire n'y sont pas recopiés. Le lot 403 fera le recalcul complet.

Décisions de l'auteur du 16 novembre 2026 appliquées ici, en plus de celles de la spec 401 :

1. **Réglage ELO absent ou illisible** : aucun ELO n'est calculé, aucune valeur de secours. La synchronisation continue : le journal reçoit tout, le téléphone vide sa file. Le serveur note « ELO à recalculer ».
2. **Affichage** : une ligne dans l'écran Profil, `ELO 1012 · provisoire` pendant la période provisoire, `ELO 1012` ensuite, rien tant qu'aucune réponse n'a compté. L'ELO est arrondi à l'entier.
3. **Même fonction que le recalcul** : le calcul au fil de l'eau applique `appliquerReponseElo` du lot 401 à chaque réponse, dans l'ordre du paquet.
4. **Réglages modifiés mais valides** : le calcul continue avec les nouveaux, et la note « ELO à recalculer » est posée.
5. **Estimation du téléphone** : il rejoue les réponses de classé de sa file à partir de la dernière valeur officielle, en prenant pour chaque question l'ELO de départ de son palier.
6. Les autres choix par défaut acceptés le même jour (onglets, lectures limitées, limite connue, création des sept clés, copie du moteur).

## 1. Objectif

Côté serveur : brancher le moteur ELO sur les traitements dérivés de la synchronisation (lot 308). À chaque paquet reçu, sous le verrou, dans l'ordre de réception :

- mettre à jour l'ELO de l'interne dans `Scores` ;
- étalonner les questions dans `Etalonnage` ;
- tenir la liste des questions déjà vues dans `Suivi` ;
- ne rien calculer si les réglages ELO ne sont pas valides, et le noter.

Côté téléphone : copier le moteur, estimer l'ELO à partir de la file, le corriger par la valeur officielle à chaque synchronisation, et l'afficher dans Profil avec la mention « provisoire ».

### 6.4 Calcul d'un paquet (`calculerLotElo`)

`calculerLotElo(entree)` — fonction pure, qui ne modifie pas son entrée.

Entrée :

```
{
  idCompte: "compte-A",
  reponses: [ <élément accepté>, … ],     // dans l'ordre du paquet
  reglagesLus: <réglages lus, lot 401>,
  questions: <indexerQuestionsElo>,        // objet vide si lotDemandeLesQuestions est faux
  interne: { elo, reponsesComptees },      // ou null : pas encore d'ELO
  etatsDesQuestions: { "Q-000001": { elo, reponsesComptees, tauxDeReussite } },   // les lignes d'Etalonnage des questions du paquet
  vues: [ 1, 2, 412 ]
}
```

Déroulé :

1. `etat = creerEtatElo()`. Y poser, en copies : `internes[idCompte]` si `interne` n'est pas nul ; `questions` = `etatsDesQuestions` ; `vues[idCompte]` = un objet `idDeQuestion(n) → true` pour chaque numéro.
2. Pour chaque réponse, dans l'ordre : `appliquerReponseElo(etat, versReponseElo(reponse, idCompte), questions, reglagesLus)`. Retenir les identifiants des questions dont `questionEtalonnee` est vrai.
3. Si `etat.internes` n'a toujours pas `idCompte` (paquet vide) : `creerEtatInterneElo(reglagesLus)`.

Sortie :

```
{
  interne: { elo, reponsesComptees },
  provisoire: true,
  interneAEcrire: true,            // interne d'entrée nul, ou état différent de l'entrée
  questions: { "Q-000006": { elo, reponsesComptees, tauxDeReussite } },   // seulement celles étalonnées par ce paquet
  vues: [ 1, 2, 6, 412 ],          // triées
  vuesChangees: true,
  sansEffet: { "<motif>": <nombre> }
}
```

**Aucune formule ici** : tout vient de `appliquerReponseElo`. C'est ce qui garantit que le recalcul du lot 403 donne le même résultat.

### 6.6 Traitement dérivé (`executerTraitementElo`)

`executerTraitementElo(contexte, dependances)` est dans `logique/elo-officiel.js`, pour se tester dans Node avec des doublures. `contexte` est celui du `lot-308.md` § 6.9.

`dependances` : `lireReglagesBruts()`, `lireEmpreinte()`, `ecrireEmpreinte(texte)`, `noterRecalcul(raison, recuLe)`, `lireLigneScores(idCompte)`, `lireQuestions()`, `lireEtalonnage()`, `ecrireScores(idCompte, ligne, cellules)`, `ecrireEtalonnage(lignesModifiees, lignesNouvelles)`.

Déroulé :

1. `contexte.reponses` vide → rend `undefined`. Rien n'est lu.
2. `bruts = lireReglagesBruts()` ; `lus = lireReglagesElo(bruts)`. Non valide → `noterRecalcul('reglages_invalides', recuLe)`, rend `undefined`. **Rien d'autre n'est lu ni écrit.**
3. `empreinte = empreinteDesReglagesElo(bruts)` ; `ancienne = lireEmpreinte()`.
   - `ancienne` nulle → `ecrireEmpreinte(empreinte)`, `noterRecalcul('premier_calcul', recuLe)` ;
   - `ancienne` différente → `ecrireEmpreinte(empreinte)`, `noterRecalcul('reglages_modifies', recuLe)` ;
   - le calcul continue dans les deux cas, avec `lus`.
4. Dans un `try` :
   1. `vues = lireVuesDuSuivi(contexte.etatSuivi)` ;
   2. `ligneScores = lireLigneScores(idCompte)` ; `interne = etatInterneDepuisScores(ligneScores)` ;
   3. si `lotDemandeLesQuestions(reponses)` : `questions = indexerQuestionsElo(lireQuestions())` et `etalonnage = lireEtalonnage()` ; sinon `questions = {}` et aucune lecture d'`Etalonnage` ;
   4. `etatsDesQuestions` : pour chaque question du paquet qui a une ligne dans `etalonnage` (la première si la question y figure deux fois), `etatQuestionDepuisEtalonnage`, sans les résultats nuls. Une question dont la ligne est vidée s'étalonne de nouveau sur cette même ligne ;
   5. `resultat = calculerLotElo(…)` ;
   6. si `resultat.questions` n'est pas vide : `ecrireEtalonnage(lignesModifiees, lignesNouvelles)`, dans l'ordre où les questions ont été étalonnées ;
   7. si `resultat.interneAEcrire` : `ecrireScores(idCompte, ligneScores, cellulesDeScores(…))`.
5. Erreur dans le `try` : `noterRecalcul('etat_illisible', recuLe)` si son code est `vues_illisibles`, `scores_illisible` ou `etalonnage_illisible` ; `noterRecalcul('ecriture_interrompue', recuLe)` sinon. **Puis l'erreur est relancée** : le lot 308 la journalise, garde l'état de `Suivi` d'avant, et répond `ok: true`.
6. Rend `ecrireVuesDansLeSuivi(contexte.etatSuivi, resultat.vues)` si `resultat.vuesChangees` ; `undefined` sinon.

L'ordre des écritures est voulu : `Etalonnage`, puis `Scores`, puis `Suivi` (écrit par le lot 308).

### 6.7 Installation et essai (`installation-elo.js`)

Quatre fonctions lancées depuis l'éditeur Apps Script, hors de la table des actions. Les trois premières lèvent une erreur si `ENVIRONNEMENT` ne vaut pas `test`.

**`installerReglagesElo()`** — crée les clés manquantes, **sans aucune valeur**. Sous `sousVerrou` :

1. `exigerEcritureDeContenuPermise()`.
2. Lit `Reglages` du fichier `ID_CONTENU`. Pour chaque clé de `DESCRIPTIONS_DES_REGLAGES_ELO` absente : une ligne `Clé`, `Valeur` vide, `Description`, `Modifié le` = `maintenant()`, `Modifié par` = `installation`. Un seul `ajouterLignes`.
3. Si au moins une ligne a été ajoutée : `contenu.version` augmente de 1, comme le fait le lot 315.
4. **Une clé déjà présente n'est jamais modifiée**, même vide ou illisible.

### 6.9 Estimation sur le téléphone

**Modifications du code du lot 309**

- Clé `elo:<ID compte>` du magasin `synchronisation` : `{ valeur, provisoire, reponsesComptees, recuLe }`. `reponsesComptees` est recopié de la réponse du serveur ; `null` s'il n'y est pas.
- `calculerEstimation(base, reponsesEnFile, estimateur)` :
  - `base` nul → `null`, comme avant ;
  - `r = estimateur(base.valeur, reponsesEnFile, base)` (troisième paramètre ajouté) ;
  - `r` est un nombre → `{ valeur: r, provisoire: base.provisoire, reponsesComptees: base.reponsesComptees ou null, estime }` ;
  - `r` est un objet → `{ valeur: r.valeur, provisoire: r.provisoire, reponsesComptees: r.reponsesComptees, estime }` ;
  - `estime` = `reponsesEnFile.length > 0`, comme avant.
- Les tests du lot 309 continuent de passer. Si l'un d'eux compare l'objet entier rendu par `calculerEstimation` ou par `lireElo`, ajoute-lui le champ `reponsesComptees` : c'est la seule adaptation permise.

**`estimerElo(base, reponsesEnFile, questionsParId, reglages)`** (`client/elo/estimation.js`, fonction pure)

- `neutre` = `{ valeur: base.valeur, provisoire: base.provisoire, reponsesComptees: base.reponsesComptees ou null }`.
- Rend `neutre` si : `base.reponsesComptees` n'est pas un entier ≥ 0 ; ou `lireReglagesElo(reglages)` n'est pas valide ; ou `questionsParId` est nul.
- Sinon, à partir de `interne = { elo: base.valeur, reponsesComptees: base.reponsesComptees }`, pour chaque enregistrement de la file, dans l'ordre :
  - `info` = `infoQuestionElo(ligne)` si `questionsParId` a la question ; `null` sinon ;
  - `effet = calculerEffetElo({ mode, reTest, resultat, reponsesProposees, interne, question: null, info, dejaVue: true }, reglagesLus)` ;
  - `interne = effet.interne`.
- Rend `{ valeur: interne.elo, provisoire: estProvisoire(interne, reglagesLus), reponsesComptees: interne.reponsesComptees }`.

Conséquences, toutes voulues :

- `question: null` : le téléphone ne connaît pas l'ELO courant des questions ; il prend l'ELO de départ du palier. L'estimation est donc approchée, et remplacée par la valeur officielle à la synchronisation suivante (`lot-309.md` § 6.7) ;
- `dejaVue: true` : le téléphone n'étalonne jamais rien ;
- seules les réponses de classé bougent l'estimation (le pré-test n'entre jamais dans la file) ;
- une réponse inexploitable (question absente du paquet, palier illisible…) est simplement sans effet.

**`demarrerElo()`** (`client/elo/branchement.js`) appelle `definirEstimateur((valeurDeBase, reponses, base) => estimerElo(base, reponses, <questionsParId du paquet « internes » en cours>, <ses reglages>))`. Le paquet est relu à chaque appel, pour suivre un rechargement du contenu. Paquet absent → `questionsParId` nul.

Le mode test n'a aucun effet ici : ses réponses n'entrent jamais dans la file (`lot-309.md` § 6.5), et l'estimateur ne lit que la file. **Ce lot n'enregistre rien de plus sur l'interne.**

## 7. Cas limites

| Cas | Comportement attendu |
|---|---|
| Une des sept clés vide (avant le lot 5) ou illisible | Rien n'est calculé ni lu. Note `reglages_invalides`. La synchronisation répond `ok: true` ; `elo` est le dernier connu, ou `null`. |
| Clé ELO présente sur deux lignes de `Reglages` | `illisible`, même conséquence. |
| Réglages corrigés ensuite | Le calcul reprend au paquet suivant. Les réponses reçues entre-temps ne sont comptées que par le recalcul (lot 403) ; la note reste posée jusque-là. |
| Réglages modifiés, valides | Le calcul continue avec les nouveaux. Note `reglages_modifies`. |
| Premier paquet après le déploiement de ce lot | Note `premier_calcul` : le journal peut contenir des réponses jamais comptées. |
| Première réponse d'un interne, en campagne ou en sprint | Sa ligne `Scores` est créée : ELO de départ, `oui`, `0`. Le téléphone n'affiche rien (aucune réponse comptée). |
| Ligne `Scores` créée par un autre lot, cellule `ELO` vide | Traitée comme un interne sans ELO ; les quatre colonnes sont écrites, `Étoiles` et `Records` ne sont pas touchées. |
| Paquet de sprint, de survie ou de jour seulement | Ni `Questions` ni `Etalonnage` ne sont lus ; `vues` est mis à jour. |
| Paquet de re-tests seulement | `Scores` créé si besoin ; rien d'autre ne change ; le traitement rend `undefined`. |
| Paquet déjà reçu (renvoi) | Le lot 308 ne passe au traitement que les réponses acceptées : rien n'est compté deux fois. |
| Réponse du mode test | Refusée par le lot 308 avant le traitement. |
| Deux installations du même compte | Le verrou les traite l'une après l'autre ; l'état est relu à chaque paquet. |
| Question archivée, ou repassée à « À valider » | Comptée normalement : seule son existence dans `Questions` importe. |
| Question sans palier lisible | Réponse sans effet (lot 401) ; la question est marquée « vue ». Le motif est compté dans le résultat, écrit nulle part. |
| Cellule illisible dans `Scores`, `Etalonnage` ou `vues` | Erreur relancée, note `etat_illisible`, rien n'est écrit. **Jamais de remise à zéro en silence.** |
| Écriture qui échoue après le calcul | Erreur relancée, note `ecriture_interrompue`. |
| **Exécution tuée entre l'écriture d'`Etalonnage` et celle de `Suivi`** | Au renvoi du téléphone, le paquet est accepté de nouveau (`lot-308.md` § 7) et compté une seconde fois dans `Etalonnage` et `Scores`. Rien ne le détecte. **Limite connue : seul le recalcul complet la répare.** Note-la dans `PROGRESS.md`. |
| Pré-test (appelé par le lot 313) | L'interne bouge ; rien dans `Etalonnage` ; `vues` inchangé. |
| Téléphone : réglages du paquet illisibles, ou paquet absent | L'estimation est la dernière valeur officielle. |
| Téléphone : `Reglages` modifié à la main sur le serveur | Le téléphone garde les réglages de son paquet jusqu'à la prochaine hausse de `contenu.version` : son estimation peut s'écarter, la valeur officielle la corrige. |
| Téléphone : serveur encore sans `reponsesComptees` | Estimation neutre ; aucune ligne dans Profil. |
| Téléphone : aucune valeur officielle reçue | `lireElo()` rend `null` ; aucune ligne. |
| Autre compte connecté sur le même téléphone | Chaque compte a sa base et sa file (`lot-309.md`) : rien à ajouter. |
