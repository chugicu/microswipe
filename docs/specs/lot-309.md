## 1. Objectif

Sur le téléphone :

- ranger chaque réponse jouée dans une file IndexedDB, sauf celles du mode test ;
- envoyer la file au serveur par paquets de 100, en arrière-plan, sans jamais faire attendre le jeu ;
- ne retirer de la file que ce que le serveur a confirmé, et renvoyer le reste après une coupure ;
- remplacer l'estimation locale de l'ELO par la valeur officielle reçue ;
- repartir proprement quand les données locales ont été effacées.

### 6.5 Mise en file

`mettreEnFile(evenement)` :

1. `filtrerEvenement(evenement)` non nul → rend `{ misEnFile: false, raison }`. **Rien n'est écrit, ni en base ni en mémoire.**
2. `compteCourant()` nul → rend `{ misEnFile: false, raison: "sans_compte" }`.
3. `depot.ajouterALaFile(…)` avec les champs de l'événement (sans `modeTest`), `compte`, `type: "reponse"`, `dateTelephone` = `maintenant()` en ISO 8601 UTC, `versionContenu` = `versionContenuLocale()`. `reponsesProposees` est recopié tel quel depuis l'événement, sans contrôle ni conversion.
4. Si l'écriture échoue : un second essai immédiat. S'il échoue aussi, la réponse est gardée dans une liste en mémoire, `stockageEnPanne` passe à vrai, et la fonction rend `{ misEnFile: false, raison: "stockage_indisponible" }`.
5. Avant toute mise en file réussie et au début de chaque `synchroniser`, la liste en mémoire est d'abord vidée dans la file, dans son ordre. Quand elle est vide, `stockageEnPanne` repasse à faux.
6. Émet `file-changee`.

L'abonné branché sur le lot 201 appelle `mettreEnFile` **sans attendre sa promesse**, et attrape ses erreurs pour qu'aucune ne remonte au jeu.

### 6.6 Envoi

`synchroniser(options)` — **un seul envoi à la fois** : un second appel pendant un envoi rend la promesse de l'envoi en cours. Le tout s'exécute dans `avecVerrouOnglets`.

1. `estEnLigne()` faux → `{ etat: "hors_ligne" }`.
2. `sessionCourante()` nulle → `{ etat: "sans_session" }`.
3. Clé `blocage` présente → `{ etat: "bloque" }`.
4. `paquet = choisirPaquet(lireTeteDeFile(idCompte, TAILLE_PAQUET))`.
5. Paquet vide : sans `memeSiVide` → `{ etat: "vide" }` ; avec `memeSiVide`, envoie un message à `elements` vide, avec l'installation courante.
6. `appelerServeur("synchroniser", { installation, elements }, { delaiMaxMs: DELAI_MAX_REQUETE_MS })`.
7. **Rejet** (réseau, délai) : la file n'est pas touchée ; planifie un renvoi (voir plus bas) ; rend `{ etat: "echec" }`.
8. **`ok: false`** : la file n'est pas touchée. Selon `decisionApresErreur(erreur)` :
   - `"session"` → `signalerSessionInvalide()` ; aucun renvoi planifié ; `{ etat: "sans_session" }` ;
   - `"bloquer"` → écrit `blocage` ; aucun renvoi jusqu'au prochain `demarrer()` ; `{ etat: "bloque" }` ;
   - `"renvoyer"` → planifie un renvoi ; `{ etat: "echec" }`.
9. **`ok: true`** : avec `interpreterReponse` :
   1. `supprimerDeLaFile(numerosASupprimer)` ;
   2. si `refus` n'est pas vide : mise à jour de la clé `refus` et un `console.warn` ;
   3. si `elo` n'est pas nul : écrit `elo:<idCompte>` = `{ valeur, provisoire, recuLe }`. **Si `elo` est nul, la valeur déjà enregistrée est gardée** ;
   4. si `versionContenu` reçue > `versionContenuLocale()` : `demanderRechargementDuContenu()` ;
   5. remet le compteur d'échecs à zéro, annule le renvoi planifié ;
   6. émet `file-changee` puis `sync-terminee`.
10. S'il reste des enregistrements du compte et que moins de `PAQUETS_MAX_PAR_CHAINE` paquets sont partis dans cet appel : retour à l'étape 4, sans `memeSiVide`. Sinon rend `{ etat: "ok" }`.

**Renvoi planifié** : `planifier(synchroniser, delaiDeRenvoi(nbEchecs))`, où `nbEchecs` compte les échecs consécutifs. Un seul renvoi planifié à la fois.

**Déclencheurs** (`declencheurs.js`) :

| Moment | Appel |
|---|---|
| Ouverture de l'appli, après `demarrer()` | `synchroniser({ memeSiVide: true })` |
| Connexion (événement du lot 303) | `synchroniser({ memeSiVide: true })` |
| Fin de partie (événement du lot 201) | `synchroniser()` |
| Événement `online` de la fenêtre | `synchroniser()` |
| `visibilitychange` vers visible | `synchroniser()` |
| `visibilitychange` vers caché | Annule le renvoi planifié. |
| File non vide après un `{ etat: "ok" }` interrompu par `PAQUETS_MAX_PAR_CHAINE` | `planifier(synchroniser, 1)` |

`declencheurs.js` fournit les vraies dépendances :

- `estEnLigne` = `navigator.onLine` ;
- `avecVerrouOnglets` = `navigator.locks.request(NOM_VERROU_ONGLETS, …)` si `navigator.locks` existe, sinon appel direct ;
- `octetsAleatoires` = `crypto.getRandomValues`.

Aucun de ces appels n'est attendu par un écran de jeu. Aucun indicateur de chargement n'est affiché.

### 6.7 Correction de l'ELO

- La **base** d'un compte est la dernière valeur officielle reçue (clé `elo:<ID compte>`).
- L'**estimation** affichée = `estimateur(base, réponses du compte encore dans la file)`.
- À chaque synchronisation réussie, la base est **remplacée** par la valeur officielle, jamais moyennée avec l'estimation. L'estimation est ensuite recalculée sur ce qui reste dans la file.
- Quand la file est vide, l'estimation est égale à la valeur officielle et `estime` vaut faux.
- Ce lot ne branche que l'estimateur neutre. Le lot 402 appellera `definirEstimateur` avec le vrai (qui lit `reponsesProposees` dans chaque enregistrement de la file).
- Ce lot n'affiche l'ELO nulle part.

### 6.8 Ligne de l'écran Profil

- Texte : `texteFileEnAttente(etatDeLaFile().enAttente)`. Ligne absente quand le texte est vide.
- Si `stockageEnPanne` est vrai, la ligne affiche à la place : « Stockage indisponible : tes réponses ne sont pas enregistrées sur ce téléphone. » **Texte proposé, à faire confirmer par l'auteur avant de l'écrire** (§ 10).
- Mise à jour sur `file-changee` et `sync-terminee`.
- Style : texte secondaire du design system, sans couleur ni espacement hors de `docs/design-system.md`.

### 6.9 Données locales effacées

- Au démarrage, `demarrer()` rend `nouvelle: true` quand la clé `installation` n'existe pas : première ouverture, nouveau téléphone, ou données effacées par Safari. Les trois cas sont traités de la même façon.
- Dans ce cas : nouvel identifiant d'installation, numéro 1, file vide, aucune base d'ELO. **Aucun message à l'interne.** La connexion et le chargement habituels (lots 303, 307, 310) ramènent le reste.
- Prévention : à la première fin de partie de chaque ouverture, si `navigator.storage` et `navigator.storage.persist` existent et que `navigator.storage.persisted()` rend faux, appelle `navigator.storage.persist()` et range sa réponse dans la clé `persistant`. Le résultat n'est pas affiché.

## 7. Cas limites

| Cas | Comportement attendu |
|---|---|
| Réponse du mode test | Jamais dans la file, ni en base ni en mémoire. |
| Mode « pré-test », « post-test » ou « duel » | Pas dans la file (`mode_hors_file`). |
| Coupure après l'écriture par le serveur, avant la réponse | La file est intacte ; au renvoi, le serveur répond `deja_recu` ; la file se vide. |
| Appli fermée pendant un envoi | Même chose à l'ouverture suivante. |
| Réponses jouées pendant un envoi | Elles restent dans la file et partent au paquet suivant. |
| Élément refusé par le serveur | Retiré de la file, compté dans `refus`. Jamais renvoyé. |
| Événement sans `reponsesProposees`, ou avec une valeur hors bornes (bug d'une mécanique) | Mis en file tel quel. Le serveur le refuse (`champ_invalide`, champ `reponsesProposees`) ; il est retiré de la file et compté dans `refus`. **Le téléphone n'invente aucune valeur.** Note-le dans `PROGRESS.md` si tu le rencontres : c'est un bug du lot de la mécanique. |
| Session expirée | File intacte, `signalerSessionInvalide()`, aucun renvoi jusqu'à la connexion suivante. |
| `occupe` ou erreur inconnue | File intacte, renvoi après 30 s, puis 60 s, 120 s, 300 s, puis 300 s. |
| `ordre_invalide`, `message_invalide`, `paquet_trop_grand` | File intacte, plus aucun envoi jusqu'à la prochaine ouverture. C'est un bug : note-le dans `PROGRESS.md` si tu le rencontres. |
| Déconnexion avec une file non vide | Les réponses restent, marquées de leur compte. |
| Un autre compte se connecte sur le même téléphone | Seules ses réponses partent ; celles du premier attendent son retour. Le compteur de Profil ne compte que le compte courant. |
| Deux onglets ouverts | Numéros attribués sans collision (transaction du dépôt) ; un seul envoi à la fois quand `navigator.locks` existe ; sinon le serveur écarte les doublons. |
| Plus de 2000 réponses en file | 20 paquets, puis la suite une seconde plus tard. |
| Écriture IndexedDB impossible | § 6.5, étapes 4 et 5. Le jeu continue sans message en cours de partie. |
| Hors ligne | Aucun appel réseau ; l'envoi repart à l'événement `online`. |
| Page en arrière-plan | Aucune minuterie active. |
| Clé `installation` absente alors que `file` n'est pas vide | Nouvel identifiant d'installation, `prochainNumero` = plus grand `numero` + 1. Les anciens enregistrements partent d'abord, dans des paquets à leur propre préfixe (`choisirPaquet`). |
| Version du contenu reçue plus grande | `demanderRechargementDuContenu()` ; ce lot ne recharge rien lui-même. |
| `elo` nul dans la réponse | La base enregistrée ne change pas. |
