# Lot 108 — Vérifications sur iPhone et Android : stockage d'une appli installée, vibration

Phase 1. Dépend des lots 103 et 104. Aucun des quatre domaines de tests obligatoires ; le lot écrit ses propres tests.
Spec écrite en phase 0, conversation B (16 novembre 2026, Opus 5.5), après les réponses de l'auteur du même jour.

Ce lot **mesure** ; il ne décide rien. Les conséquences de ses résultats sont tranchées par l'auteur, sauf une, décidée d'avance (décision 3).

Décisions de l'auteur du 16 novembre 2026 appliquées ici :

1. Les vérifications se font sur la version publiée par GitHub Pages (`https://chugicu.github.io/microswipe/`, lot 103), seul moyen d'avoir une adresse HTTPS sur le téléphone.
2. **iPhone et Android** sont vérifiés tous les deux, sur les téléphones de l'auteur.
3. **Si la vibration ne marche pas sur iPhone**, le réglage « Vibration en cas d'erreur » (G14) sera **masqué là où elle ne marche pas** ; le retour d'erreur reste visuel partout. Le lot qui codera G14 appliquera cette règle. Aucun contournement n'est essayé.

## 1. Objectif

Répondre, par la mesure, aux questions laissées ouvertes par l'architecture (§ 3, § 7) et le briefing (§ 9, G14 ; § 13) :

1. une appli installée sur l'écran d'accueil partage-t-elle son stockage avec le navigateur ? (Sinon : connexion et Face ID propres à MicroSwipe, lot 303.)
2. la vibration web marche-t-elle, sur iPhone et sur Android, dans le navigateur et dans l'appli installée ?
3. et, au passage : stockage persistant, place disponible, détection de l'installation et du moyen d'installer (lot 103), ouverture hors ligne, verrouillage en portrait, disponibilité de l'authentification par le téléphone (utile au verrou Face ID, lot 303).

## 6. Interfaces

### 6.1 Ouverture de la page

- `client/demarrage.js` : si l'ancre de l'adresse vaut exactement `#verifications-108`, il charge `client/verifications/page-108.js` (import dynamique) **à la place de la coquille vide**, après l'accueil. Sinon, rien ne change.
- Dans l'appli installée, l'adresse ne se tape pas. L'auteur ouvre donc la page dans l'appli installée par le moyen que le système permet (par exemple un lien ouvert depuis l'appli, ou une installation faite depuis l'adresse qui porte l'ancre) ; si aucun ne marche, arrête-toi et demande, sans modifier le manifeste.
- Cette page est réservée à l'auteur. Elle sera retirée à la recette (lot 319 ; contrat ajouté à l'index). Ses textes sont techniques et ne demandent pas de validation.

### 6.2 Fonctions pures (`client/verifications/regles.js`)

| Fonction | Entrée → sortie |
|---|---|
| `creerMarqueur(octets, date)` | `octets` : 6 octets aléatoires ; `date` : texte ISO 8601. → `{ code, date }`, `code` = 6 caractères dans `[a-z0-9]`. |
| `comparerMarqueurs(ecrit, lu)` | → `partage` si `lu` a le même `code` ; `separe` si `lu` est nul ; `autre` si `lu` a un autre code (marqueur d'une mesure précédente). |
| `resumerMesures(mesures)` | `mesures` : objet de résultats (§ 6.3). → un texte de compte rendu, une ligne par mesure, sans aucune donnée personnelle ni identifiant de compte. |

Bouton « Lire le marqueur » : affiche le code lu, ou « aucun ». L'auteur écrit dans le navigateur, lit dans l'appli installée, puis l'inverse. | `partage`, `separe` ou `autre`, pour chaque sens. |

## 8. Tests à écrire

`node --test`, sans dépendance, **aucune donnée personnelle**.

1. `creerMarqueur` : octets à 0, à 255, quelconques → `code` conforme à `^[a-z0-9]{6}$`, `date` recopiée.
2. `comparerMarqueurs` : même code → `partage` ; lu nul → `separe` ; autre code → `autre`.
3. `resumerMesures` : un objet de mesures fictif → une ligne par mesure, dans l'ordre M1 à M9 ; une mesure absente → « non mesuré ».
4. Les tests du lot 103 passent toujours, dont le test 9 (`client/verifications/` hors de la coquille) et le test 8 (versions égales).
5. Aucun fichier du lot ne contient `localStorage`, `sessionStorage` ni `deleteDatabase('microbio')` ; `deleteDatabase` n'y vise que `microbio-essai-108`.
