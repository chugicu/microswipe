# Lot 104 — Stockage local IndexedDB : enveloppe et migrations

Phase 1. Dépend du lot 101. Aucun des quatre domaines de tests obligatoires ; le lot écrit ses propres tests.
Spec écrite en phase 0, conversation B (16 novembre 2026, Opus 5.5).

Ce lot fournit ce que les specs 208 et 309 attendent du lot 104 (index des lots, « Contrats déjà fixés ») : ajout de magasins et d'index par migration, transactions en écriture sur plusieurs magasins, clés composées.

Choix **confirmés par l'auteur le 17 novembre 2026** (proposés par défaut à la conversation B, sans question) :

1. **Une seule base**, nommée `microbio`. IndexedDB est partagé par toutes les applis de `chugicu.github.io` : le nom évite toute collision avec Carnet Réa et EchoLearn.
2. **Migrations déclaratives** : une migration est une donnée (liste d'étapes « créer un magasin », « créer un index »), pas une fonction. Elle se vérifie donc sans navigateur. Une migration publiée n'est jamais modifiée ni retirée.
3. **Clés en ligne seulement** : la clé d'un enregistrement est un de ses champs, ou plusieurs pour une clé composée. Pas de clé à part, pas de numérotation automatique.
4. Aucune suppression de magasin ni de données par une migration dans ce lot. Le jour où un lot en aura besoin, il l'ajoutera à l'enveloppe, avec l'accord de l'auteur.
5. **Une base en mémoire, de même interface**, rangée dans `tests/`, pour que les lots suivants testent leur stockage dans Node sans dépendance. Les mêmes scénarios tournent sur la vraie base dans une page de vérification.
6. Quand un autre onglet ouvre une version plus récente de la base, celle-ci est fermée et un événement le signale. Proposer de recharger la page est l'affaire du lot 103 (mise à jour de l'appli).

## 1. Objectif

Écrire l'enveloppe par laquelle **tout** le stockage local du client passe :

- ouvrir la base, en appliquant les migrations manquantes ;
- lire, écrire et supprimer des enregistrements, par clé simple ou composée, et par index ;
- grouper plusieurs opérations sur plusieurs magasins dans une transaction : tout ou rien ;
- traduire les erreurs du navigateur en codes que les lots suivants savent traiter.

Ce lot ne crée aucun magasin métier : chaque lot ajoute le sien par une migration (lot 107 : `contenu` ; lot 208 : `progression` ; lot 309 : `file` et `synchronisation`…).

## 6. Interfaces

### 6.1 Codes d'erreur

Une erreur prévue est un `Error` dont `message` et `code` valent le code, créé par `creerErreurDeStockage(code)`.

| Code | Cause |
|---|---|
| `stockage_indisponible` | `indexedDB` absent, ou ouverture refusée par le navigateur (navigation privée, réglage, disque). |
| `migration_invalide` | La liste des migrations ne tient pas les règles du § 6.3 : rien n'est ouvert. |
| `migration_echouee` | Une étape a échoué pendant la mise à niveau : la base reste à son ancienne version. |
| `version_plus_recente` | La base enregistrée a une version plus grande que le code (retour à une ancienne version de l'appli). |
| `base_bloquee` | Une autre connexion empêche la mise à niveau au-delà de `ATTENTE_BLOCAGE_MS`. |
| `base_fermee` | Opération demandée sur une base fermée (par `fermer()` ou par un autre onglet). |
| `magasin_inconnu` | Magasin ou index absent du schéma. |
| `magasin_hors_transaction` | Opération, dans une transaction, sur un magasin qu'elle ne couvre pas. |
| `transaction_en_lecture` | Écriture demandée dans une transaction en lecture. |
| `cle_invalide` | Clé absente de l'enregistrement, ou d'un type que les clés n'admettent pas (§ 6.2). |
| `requete_invalide` | Requête de lecture mal formée (§ 6.5). |
| `valeur_non_clonable` | Valeur qui ne se copie pas (fonction, objet du navigateur…). |
| `quota_depasse` | Plus de place pour ce site. |
| `transaction_inactive` | Opération demandée après que la transaction s'est terminée (§ 6.6, règle du travail). |
| `transaction_echouee` | Toute autre erreur de transaction. |

### 6.2 Fonctions pures (`regles.js`)

Aucun accès à `indexedDB`, `window`, `document`, `localStorage`, `Date.now`, `Math.random`. Aucune fonction ne modifie ce qu'elle reçoit.

| Fonction | Entrée → sortie |
|---|---|
| `creerErreurDeStockage(code)` | → `Error` avec `message` et `code`. |
| `estCleValide(cle)` | → vrai pour : un nombre qui n'est pas `NaN` ; un texte ; une date dont l'heure est valide ; un tableau, vide ou non, de clés valides, sans boucle. Faux pour tout le reste (`true`, `null`, `undefined`, objet). |
| `comparerCles(a, b)` | → −1, 0 ou 1, dans l'ordre d'IndexedDB : nombre < date < texte < tableau ; nombres par valeur, dates par heure, textes par unités de code, tableaux élément par élément puis par longueur. `a` ou `b` invalide → lève `cle_invalide`. |
| `extraireCle(valeur, cheminDeCle)` | `cheminDeCle` : un nom de champ, ou un tableau de noms. → la clé (un tableau pour une clé composée). Champ absent ou clé invalide → lève `cle_invalide`. |
| `bornesDuPrefixe(prefixe)` | `prefixe` : tableau de clés valides. → `{ depuis: prefixe, jusqua: [...prefixe, []] }` : toutes les clés composées qui commencent par `prefixe` (un tableau vide se classe après tout nombre, date ou texte). |
| `validerMigrations(migrations)` | → tableau de défauts `{ version, regle }`, vide si tout va bien (règles du § 6.3). |
| `simulerSchema(migrations)` | → le schéma obtenu en appliquant toutes les migrations : `{ version, magasins: { <nom>: { cle, index: { <nom>: { cle, unique } } } } }`. Défauts → lève `migration_invalide`. |
| `migrationsAAppliquer(migrations, ancienneVersion)` | → les migrations de version strictement supérieure à `ancienneVersion`, dans l'ordre. |
| `verifierRequete(requete, schemaDuMagasin)` | → la requête normalisée, ou lève `requete_invalide` / `magasin_inconnu` (§ 6.5). |

### 6.3 Migrations (`migrations.js`)

| Constante | Valeur |
|---|---|
| `NOM_BASE` | `microbio` |
| `MIGRATIONS` | Tableau de migrations, dans l'ordre des versions. Dans ce lot : la migration 1 seulement. |

**Forme d'une migration** :

```
{
  version: 1,
  lot: "104",
  description: "Création de la base",
  etapes: []
}
```

**Étapes admises** :

| Étape | Champs | Effet |
|---|---|---|
| `creerMagasin` | `magasin` (nom), `cle` (nom de champ, ou tableau de noms) | Crée un magasin dont la clé est en ligne. |
| `creerIndex` | `magasin`, `index` (nom), `cle` (nom de champ, ou tableau de noms), `unique` (booléen) | Crée un index sur un magasin existant. |

Exemple d'étapes, pour un lot futur (forme seulement) : `{ etape: "creerMagasin", magasin: "file", cle: "numero" }`, puis `{ etape: "creerIndex", magasin: "file", index: "compte-numero", cle: ["compte", "numero"], unique: false }`.

**Règles** (vérifiées par `validerMigrations`) :

| `regle` | Défaut |
|---|---|
| `version` | Les versions ne sont pas 1, 2, 3… sans trou ni doublon, dans l'ordre du tableau. |
| `description` | `lot` ou `description` n'est pas un texte non vide. |
| `etape_inconnue` | Une étape n'est ni `creerMagasin` ni `creerIndex`, ou un champ attendu manque. |
| `nom_invalide` | Un nom de magasin ou d'index ne correspond pas à `^[a-z][a-z0-9-]*$`. |
| `cle_invalide` | `cle` n'est ni un texte non vide, ni un tableau d'au moins deux textes non vides et distincts. |
| `magasin_existant` | Magasin déjà créé par une migration précédente ou par une étape précédente. |
| `magasin_inconnu` | Index sur un magasin qui n'existe pas encore. |
| `index_existant` | Même nom d'index deux fois sur un magasin. |

**Règles de travail**, à écrire en tête de `migrations.js` :

- un lot qui a besoin d'un magasin ou d'un index **ajoute une migration à la fin**, avec la version suivante ;
- une migration déjà enregistrée sur `dev` n'est **jamais** modifiée, renumérotée ni retirée : des navigateurs l'ont peut-être déjà appliquée ;
- la version de la base est le nombre de migrations.

### 6.4 Ouvrir la base (`base-locale.js`)

**`ouvrirBase({ nom, migrations, fabrique })`** → promesse d'une base (§ 6.5).

- `fabrique` : l'objet `indexedDB` ; par défaut `globalThis.indexedDB`.
- `ATTENTE_BLOCAGE_MS` : 5 000.

Déroulé :

1. `validerMigrations(migrations)` non vide → rejet `migration_invalide`. Rien n'est ouvert.
2. `fabrique` absente → rejet `stockage_indisponible`.
3. Ouverture de `nom` à la version `migrations.length`.
4. **Mise à niveau** (événement `upgradeneeded`) : pour chaque migration de `migrationsAAppliquer(migrations, ancienneVersion)`, chaque étape, dans l'ordre. Une erreur → la mise à niveau est annulée, rejet `migration_echouee` ; la base reste à son ancienne version.
5. **Blocage** (événement `blocked`) : si la mise à niveau n'a pas pu se faire au bout de `ATTENTE_BLOCAGE_MS`, rejet `base_bloquee`.
6. Erreur de version (base enregistrée plus récente) → rejet `version_plus_recente`. **La base n'est jamais supprimée** pour repartir de zéro.
7. Toute autre erreur d'ouverture → rejet `stockage_indisponible`.
8. Succès : la base est rendue ; un gestionnaire `versionchange` la ferme dès qu'un autre onglet demande une version plus récente, puis émet `base-perimee` (§ 6.5).

Aucune fonction du client n'appelle `deleteDatabase` sur `NOM_BASE`. Seule la page de vérification supprime sa propre base d'essai (§ 8.4).

### 6.5 La base

Même interface pour la vraie base et pour la base en mémoire. Toutes les fonctions rendent une promesse.

| Membre | Rôle |
|---|---|
| `version` | Entier : la version ouverte. |
| `schema` | Le résultat de `simulerSchema(migrations)`. |
| `lire(magasin, cle)` | → l'enregistrement, ou `null` s'il n'existe pas. |
| `lireTout(magasin, requete)` | → tableau d'enregistrements, dans l'ordre croissant de la clé (ou de la clé de l'index). |
| `compter(magasin, requete)` | → nombre d'enregistrements. |
| `ecrire(magasin, valeur)` | Crée ou remplace l'enregistrement de même clé. → la clé. |
| `ecrirePlusieurs(magasin, valeurs)` | Tout ou rien, dans une seule transaction. |
| `supprimer(magasin, cle)` | Sans erreur si la clé n'existe pas. |
| `supprimerPlusieurs(magasin, cles)` | Tout ou rien. |
| `vider(magasin)` | Supprime tous les enregistrements du magasin. |
| `transaction(magasins, mode, travail)` | § 6.6. |
| `fermer()` | Ferme la base ; toute opération suivante rejette `base_fermee`. |
| `evenements` | Un `EventTarget` qui émet `base-perimee` quand un autre onglet a fermé la base. |

**Requête** de `lireTout` et `compter` — un objet, tous les champs facultatifs :

| Champ | Sens |
|---|---|
| `index` | Nom d'un index du magasin ; absent → la clé du magasin. |
| `cle` | Une clé exacte. |
| `prefixe` | Un tableau : les clés composées qui commencent par lui (`bornesDuPrefixe`). |
| `depuis`, `jusqua` | Bornes incluses. |
| `limite` | Entier ≥ 1 : les premiers enregistrements seulement (`lireTout`). |

`cle`, `prefixe` et le couple `depuis` / `jusqua` s'excluent. Un champ inconnu, une clé invalide, une `limite` qui n'est pas un entier ≥ 1, un `prefixe` qui n'est pas un tableau → `requete_invalide`. Un `index` inconnu → `magasin_inconnu`. Requête absente → tout le magasin.

Exemple (forme seulement) : les 100 premières réponses d'un compte dans la file du lot 309 = `lireTout("file", { index: "compte-numero", prefixe: ["compte-A"], limite: 100 })`.

**Valeurs** : un enregistrement est copié à l'écriture et à la lecture (copie structurée du navigateur). Modifier un objet lu ne change pas la base. Une valeur qui ne se copie pas → `valeur_non_clonable`.

### 6.6 Transactions

**`transaction(magasins, mode, travail)`**

- `magasins` : tableau de noms ; `mode` : `lecture` ou `ecriture`.
- `travail(t)` reçoit un objet qui a `lire`, `lireTout`, `compter`, `ecrire`, `supprimer` et `vider`, limités aux magasins listés, et rend une promesse ou une valeur.
- → une promesse de la valeur rendue par `travail`, **une fois la transaction terminée et enregistrée**.
- Si `travail` lève ou rejette : la transaction est annulée, **rien de ce qu'elle a écrit n'est gardé**, et la promesse rejette avec la même erreur.
- Écriture en mode `lecture` → `transaction_en_lecture` ; magasin non listé → `magasin_hors_transaction` ; dans les deux cas la transaction est annulée.

Exemple (forme seulement) : attribuer un numéro et ranger une réponse en une seule fois, comme le fait `ajouterALaFile` du lot 309 = une transaction en écriture sur `synchronisation` et `file`, qui lit le compteur, l'augmente, et écrit l'enregistrement.

**Règle du travail**, à écrire en commentaire de la fonction et dans `PROGRESS.md` : **dans `travail`, n'attends que les opérations de `t`.** Attendre autre chose (un appel réseau, une minuterie, une autre base) laisse le navigateur clore la transaction : ce qui a été écrit avant est enregistré, et l'opération suivante rejette `transaction_inactive`. Lis ce qu'il faut avant la transaction, calcule dedans sans rien attendre d'autre.

### 6.7 Instance de l'appli (`base-locale.js`)

**`ouvrirBaseDuJeu()`** → la promesse d'`ouvrirBase({ nom: NOM_BASE, migrations: MIGRATIONS })`, gardée pour les appels suivants. Si elle rejette, l'appel suivant réessaie.

Ce lot ne l'appelle pas au démarrage de l'appli : le premier lot qui s'en sert est le lot 107. Les lots suivants n'appellent jamais `ouvrirBase` eux-mêmes pour la base de l'appli. Un échec d'ouverture n'arrête pas le jeu : chaque lot garde alors ses données en mémoire, comme le prévoient les specs 208 (§ 6.7) et 309 (§ 6.5).

### 6.8 Base en mémoire (`tests/client/stockage/base-memoire.js`)

**`creerBaseEnMemoire({ migrations, versionEnregistree })`** → promesse d'une base de l'interface du § 6.5.

- Valide et simule les migrations comme `ouvrirBase` (mêmes rejets `migration_invalide` et, si `versionEnregistree` dépasse `migrations.length`, `version_plus_recente`).
- Range les enregistrements dans des `Map`, trie par `comparerCles`, copie les valeurs par `structuredClone` (`valeur_non_clonable` sinon).
- Exécute les transactions l'une après l'autre ; une transaction travaille sur une copie des magasins qu'elle couvre et ne la garde qu'à la fin réussie de `travail`.
- `rouvrir(nouvellesMigrations)` : rend une nouvelle base sur les mêmes données, après les migrations manquantes, pour tester une mise à niveau.
- Ne détecte pas la règle du travail (§ 6.6) : seule la page de vérification le peut.

Elle sert aux tests de ce lot et aux tests des lots suivants (107, 208, 209, 309…). Elle n'est jamais importée par le code de `client/`.

## 7. Cas limites

| Cas | Comportement attendu |
|---|---|
| Navigation privée, ou IndexedDB désactivé | `ouvrirBaseDuJeu` rejette `stockage_indisponible` ; aucune erreur non gérée ; le jeu continue en mémoire (lots suivants). |
| Première ouverture | Toutes les migrations s'appliquent ; version = nombre de migrations. |
| Ouverture après l'ajout d'une migration | Seules les nouvelles s'appliquent ; les données existantes sont intactes. |
| Base plus récente que le code | `version_plus_recente` ; la base n'est ni supprimée ni modifiée. |
| Deux onglets, l'un mis à jour | L'ancien onglet ferme sa base et émet `base-perimee` ; la mise à niveau du nouvel onglet se fait. |
| Mise à niveau bloquée plus de 5 secondes | `base_bloquee`. |
| Erreur pendant une migration | `migration_echouee` ; la base reste à son ancienne version, sans magasin à moitié créé. |
| `lire` d'une clé absente | `null`. |
| Clé composée dont un champ manque dans la valeur | `cle_invalide` ; rien n'est écrit. |
| Clé de type booléen ou objet | `cle_invalide`. |
| `lireTout` par préfixe d'une clé composée | Seuls les enregistrements qui commencent par le préfixe, triés par la suite de la clé. |
| `limite` absente | Tout ce qui correspond. |
| `travail` lève après deux écritures | Aucune des deux n'est gardée. |
| `travail` attend une minuterie puis écrit (vraie base) | L'écriture rejette `transaction_inactive` ; ce qui a été écrit avant la minuterie est gardé. C'est la raison de la règle du travail. |
| Écriture d'une fonction ou d'un objet du navigateur | `valeur_non_clonable`. |
| Quota dépassé | `quota_depasse` ; l'appelant garde la donnée en mémoire. |
| Opération après `fermer()` | `base_fermee`. |
| Nom de magasin ou de champ égal à une propriété d'objet (`constructor`) | Traité comme un nom ordinaire. |

### 8.3 Scénarios communs (`scenarios.js`)

Chaque scénario est une fonction qui reçoit une fabrique de base (mémoire ou vraie) et des migrations d'essai, et lève en cas d'écart. Migrations d'essai : magasin `essai-simple` (clé `id`) ; magasin `essai-compose` (clé `["compte", "niveau"]`) ; magasin `essai-file` (clé `numero`, index `compte-numero` sur `["compte", "numero"]`) ; magasin `essai-meta` (clé `cle`).

1. Base neuve : `version` = nombre de migrations ; les quatre magasins existent.
2. `ecrire`, `lire`, `supprimer` sur `essai-simple` ; `lire` d'une clé absente → `null`.
3. Clé composée : trois enregistrements pour `compte-A`, deux pour `compte-B` ; `lire(["compte-A", "NIV-0002"])` ; `lireTout` par préfixe `["compte-A"]` → les trois, triés par niveau.
4. Index composé : six enregistrements de `essai-file` mêlant deux comptes ; `lireTout` par index et préfixe `["compte-B"]`, `limite` 2 → les deux plus petits numéros de `compte-B`.
5. `compter` : tout le magasin ; par préfixe.
6. **Transaction sur deux magasins** : lit un compteur dans `essai-meta`, l'augmente, écrit un enregistrement dans `essai-file` avec ce numéro → les deux écritures sont visibles après.
7. **Tout ou rien** : `travail` écrit dans deux magasins puis lève → aucune des deux écritures n'est gardée ; la promesse rejette avec la même erreur.

11. Clé composée dont un champ manque → `cle_invalide`, rien n'est écrit.
12. Valeur non copiable (une fonction) → `valeur_non_clonable`.
13. Copie des valeurs : modifier un objet lu, puis relire → valeur d'origine.
